# 迭代 2 报告：B 知识接入召回改进（方案 A：有限正文回退）

> 日期：2026-11-14 · 版本：0.3.0（召回改进）+ 0.3.1（精度修订）· 契约：`knowledge-card` v1.0 · 状态：已交付

## 1. 背景与决策

迭代 1a 的 PoC 得出结论：

- 现有 `search` 表是 APP 私有 tokenizer 写入的 FTS5 contentless 索引，外部 `MATCH` 命中为 0，**不能复用**；
- 元数据候选依赖 `documents.path/title` 含查询词，而 05/06 的剧本文件名通常不含主题词，导致剧本通道召回明显弱于 08 方法书；
- 证据链本身成立（只读、行级、不虚构），问题只在**召回**。

用户在两个方案中选择 **A：有限正文扫描回退**（先做、成本低）；**B：按契约重建索引**保留为中期方案。

## 2. 实现范围

| 模块 | 变更 |

| `packages/knowledge_service/adapter.py` | 新增 `list_scan_files()`：在 lane 允许分类内按 `(category, path)` 固定顺序列出文档行，不按查询词过滤；沿用分类白名单与路径排除 |

| `packages/cli/main.py` | 新增 `--no-fallback` / `--fallback-files` / `--fallback-bytes`；文本输出新增回退统计行 |

### 2.1 触发条件

任一满足即触发回退：

1. `evidence_below_limit`：已形成证据数少于 `evidence_limit`；
2. `lane_without_candidates`：某个查询 lane 的元数据候选为 0。

不触发时不会读取任何额外正文，保持原 PoC 的低成本路径。

### 2.2 预算与顺序

- `fallback_max_files`：默认 200 份文件；
- `fallback_max_bytes`：默认 256KB/文件；
- 只扫描 `.md` / `.txt`，文件必须真实存在于知识库根之下；
- 列举顺序固定为 `(category, path)`，结果可复现；元数据已取证的路径不重复扫描；
- 预算耗尽即停止；命中后证据与候选分别按 `evidence_limit` / `candidates_limit` 截断。

### 2.3 只读保证

回退只读正文文件，不执行 SQL 写操作。真实库实测检索前后 `knowledgeIndex.sqlite`：

- SHA-256：`49D3D4053D9F89035587AB7F685B2DC244D0E44F5823C2BFD061FA4B1E227F29`（前后一致）；
- 大小 76,800,000 字节、mtime 均未变化。

## 4. 精度观察（必须如实记录）

回退使用字面子串匹配，本轮 8 条证据中至少 3 条属于**非结构性误命中**：

- 「反转身倚在窗边」（动作描写，非情节反转）；
- 「把宣传册反转过来」（物体翻转）；
- 「女主幻想今晚和帅哥洞房但反转男人说主卧宽敞」（语料本身的叙述词，语义偏移）。

因此本轮召回提升是**真实但精度不足**：它能证明「预算内可以找到未召回剧本正文」，不能直接当作「可迁移方法」交付创作。后续精度改进建议：

1. 多词共现打分（如「反转」需与「伏笔/真相/身份/结局」共现）；
2. 短语优先（「反转设计」「身份反转」「情节反转」加权）；
3. 词边界/上下文窗口过滤明显动作动词搭配；
4. 候选排序引入 kind 与 category 权重，而非仅按路径顺序。

## 7. 迭代 2.1（v0.3.1）精度修订实测

针对第 4 节的误命中，0.3.1 落地了四层精度策略（实现细节见 `docs/knowledge-service.md` §2.5）：动作/物件误命中过滤、结构语境词加权、常见叙事搭配短语加权、多词共现加权；高置信证据足够时丢弃纯字面低置信证据。

最终证据（同一文件，均为结构性表述）：

取舍说明：精度提升以牺牲部分召回为代价（证据 8→2）；这是「宁可少给、不可虚构」的定向选择，完整召回仍依赖方案 B。

## 8. 结论

方案 A 达标：在只读、可关闭、预算明确的前提下，把「元数据召回 0」的剧本检索从不可用提升为「可找到并有行级证据」；同时保留了不虚构命中的底线，并把精度问题显式留在后续迭代处理。
